# از موضوع تا پروژه با project-builder

این اسکیل موضوع اولیه را با پرسش‌وپاسخ به سناریو، نیازمندی، طراحی و پروژهٔ قابل اجرا تبدیل می‌کند. سه حالت دارد: فقط نیازسنجی، فقط طراحی، یا طراحی و ساخت. اسکیل خودکفاست؛ از اسکیل‌های موجود فقط وقتی مرتبط و در دسترس باشند استفاده می‌کند. هیچ مدل یا اسکیلی نبود تمام باگ‌ها یا بهترین پاسخ مطلق را تضمین نمی‌کند.

## شروع سریع: موضوع اولیه و ساخت

```text
با project-builder موضوع «سامانهٔ رزرو نوبت برای یک کلینیک» را به پروژهٔ قابل اجرا تبدیل کن.
مقصد پروژه: C:/work/clinic-booking. زبان رابط و مستندات: فارسی با RTL.
ابتدا با چند سؤال کوتاه کاربران، گردش‌کار، دامنه، فناوری، محدودیت و معیار پذیرش را مشخص کن.
پاسخ‌های لازم را از من بگیر؛ فرض‌ها را صریح بنویس و جواب من را حدس نزن.
سناریوی اصلی، جایگزین و شکست، نقش‌ها، صفحات، داده، API، امنیت و تست‌ها را طراحی کن.
بعد از روشن‌شدن تصمیم‌های مهم، دامنهٔ توافق‌شده را مرحله‌ای بساز و تست کن.
هیچ deployment، سرویس پولی، push یا انتشار خارجی انجام نده.
```

این پیام مجوز ساخت در مقصد مشخص‌شده را می‌دهد. اگر آن مسیر پروژهٔ موجود دارد، ابتدا آن را بررسی می‌کند و تغییرات سازگار پیشنهاد می‌دهد؛ بازنویسی کامل به‌صورت ضمنی مجاز نیست. مشخص‌نبودن فناوری مانع ارائهٔ پیشنهاد نیست، ولی محدودیت متعلق به کاربر باید پرسیده شود.

## فقط سناریو و طراحی؛ بدون ساخت

```text
با project-builder برای «مدیریت موجودی فروشگاه» نیازسنجی و سناریوی جامع تولید کن.
فعلاً کد تولید یا تغییر نده؛ پس از پرسش‌وپاسخ، نیازمندی‌ها، نقش‌ها، جریان‌ها و خطاها را بده.
MVP، امکانات آینده، موجودیت‌ها، قوانین کسب‌وکار، معماری پیشنهادی و معیارهای پذیرش را جدا کن.
فرضیات و تصمیم‌های باز را مشخص کن. طراحی متناسب با اندازه و بودجهٔ واقعی باشد.
```

## نمونهٔ تعامل و تبدیل پاسخ به معیار پذیرش

نمونهٔ زیر فرضی است و جواب کاربر واقعی محسوب نمی‌شود:

1. اسکیل می‌پرسد: چه کسانی از سامانه استفاده می‌کنند و سه کار ضروری آن‌ها چیست؟
2. پاسخ نمونه: مراجعه‌کننده نوبت می‌گیرد؛ پذیرش آن را تغییر می‌دهد؛ مدیر ساعات پزشک را تنظیم می‌کند.
3. اسکیل می‌پرسد: پرداخت آنلاین، چند شعبه و پیامک برای نسخهٔ اول لازم‌اند؟ محدودیت فناوری یا محل میزبانی چیست؟
4. پاسخ نمونه: فعلاً یک شعبه، بدون پرداخت و پیامک؛ اجرای محلی برای نمایش؛ انتخاب فناوری با پیشنهاد شما.
5. اسکیل خلاصهٔ تصمیم‌ها و سناریوی مشخص را ارائه می‌کند؛ فقط دربارهٔ ابهام‌های مؤثر سؤال بعدی می‌پرسد، مانند سیاست لغو یا جلوگیری از رزرو هم‌زمان.

برای نیاز «یک زمان را دو نفر نگیرند»، معیار آزمون پیشنهادی:

```text
REQ-BOOK-01
Given: یک بازهٔ آزاد برای پزشک تعریف شده است.
When: دو درخواست رزرو مستقل برای همان بازه هم‌زمان ثبت شوند.
Then: دقیقاً یک رزرو موفق باشد؛ درخواست دیگر خطای قابل فهم بگیرد؛
دادهٔ ذخیره‌شده فقط یک رزرو فعال برای آن بازه داشته باشد.
```

این تست تا زمانی که اجرا نشده، «پیشنهادی» است. اجرای نمایش محلی به معنی تأیید آماده‌بودن برای production نیست.

## جزئیاتی که متناسب با پروژه بررسی می‌شوند

| بخش | خروجی مورد انتظار |
| --- | --- |
| مسئله و دامنه | کاربران، هدف، امکانات ضروری، موارد خارج از دامنه، موفقیت قابل اندازه‌گیری |
| سناریو و تجربهٔ کاربر | جریان اصلی و جایگزین، خطا/بازیابی، stateها، صفحات و navigation، RTL و دسترس‌پذیری |
| داده و قرارداد | موجودیت، مالکیت، قوانین و constraints، API/events، migrations، نگهداری و حذف داده |
| امنیت و قابلیت اطمینان | نقش/مجوز، secrets، اعتبارسنجی، درخواست تکراری، concurrency و قطع integration مرتبط |
| معماری و اجرا | دلیل انتخاب stack، ماژول‌ها، نمودار قابل ویرایش، config، محیط‌ها و وابستگی‌ها |
| برنامهٔ ساخت | برش قابل اجرای اولیه، مراحل وابسته، MVP و قابلیت‌های آینده |
| تأیید و تحویل | نگاشت نیاز به تست، نتیجهٔ واقعی checks، setup/start، محدودیت، نصب/ارتقا/rollback |

همهٔ پروژه‌ها به API، پایگاه داده یا cloud نیاز ندارند. در پروژهٔ ساده، این بخش‌ها تا حد لازم خلاصه یا حذف می‌شوند؛ کامل‌بودن به معنی معماری پیچیده‌تر نیست.

برای پروژهٔ جدید، ساختار مستندات پیشنهادی می‌تواند `docs/project-brief.md`، `docs/scenarios.md`، `docs/design.md` و `docs/verification.md` باشد؛ در پروژهٔ موجود از قرارداد همان repository استفاده می‌شود. تصمیم‌های اصلی در یک brief ثبت می‌شوند تا پرسش‌ها و متن‌های قبلی تکرار نشوند.

## ترکیب و ادامه در جلسهٔ بعد

```text
با task-orchestrator و project-builder پروژهٔ «داشبورد هزینه‌های شخصی» را طراحی و بساز.
از project-docs فقط برای مستندات و نمودارهای نهایی استفاده کن.
اگر پوشش تست نامشخص بود از test-gap-analysis کمک بگیر؛ برای نقص اثبات‌شده
audit-remediation یا audit-fix-loop را در مرحلهٔ مرتبط اجرا کن، نه حلقه‌های تو در تو.
brief و ledger مشترک نگه دار. اجازهٔ انتشار خارجی نداریم.
```

```text
با project-builder ادامهٔ پروژه را از docs/project-brief.md و docs/verification.md انجام بده.
تصمیم‌های تأییدشده را دوباره نپرس؛ اگر شواهد یا دامنه تغییر کرده، اختلاف را مشخص کن.
نیازهای باقی‌مانده را مرحله‌ای تکمیل و نتایج تست را به‌روز کن.
```

برای کمترین context، فقط brief، مرحلهٔ جاری و اسکیل‌های لازم خوانده می‌شوند؛ بررسی ضروری، سؤال مؤثر و تست لازم برای کاهش توکن حذف نمی‌شوند. اگر integration یا ابزار تست در دسترس نباشد، وضعیت ناتمام همراه دلیل گزارش می‌شود؛ mock نباید موفقیت واقعی معرفی شود.

## نصب انتخابی

از پوشهٔ بسته اجرا کنید؛ در agentهایی که نام‌های dollar یا slash را پشتیبانی می‌کنند می‌توان از selector نیز استفاده کرد. پیام معمولی با نام اسکیل قابل‌حمل‌تر است.

<div dir="ltr">

```powershell
./install.ps1 -GlobalOnly -Agents all -Skills project-builder -WhatIf
./install.ps1 -GlobalOnly -Agents all -Skills project-builder
```

```bash
bash ./install.sh --global-only --agents all --skills project-builder --dry-run
bash ./install.sh --global-only --agents all --skills project-builder
```

</div>

برای نصب پروژه‌ای از ProjectOnly/ProjectPath یا project-only/project استفاده کنید. انتخاب `project-builder` اسکیل پایهٔ enterprise-audit را نیز نصب می‌کند؛ سایر اسکیل‌ها خودکار نصب نمی‌شوند. اسکیل‌های اختیاری مفقود، مانع اجرای مستقیم کار در محدودهٔ توانایی agent نیستند. راهنمای [نصب](installation.md) و [مسیرهای سراسری](global-installation.md) را ببینید.
