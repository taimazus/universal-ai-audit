# نمونه‌های کامل استفادهٔ تکی

هر بلوک زیر یک پیام قابل کپی برای agent است. مسیرهای نمونه و نام branch را با مقادیر واقعی پروژه عوض کنید. گزارش‌های پیش‌فرض فارسی‌اند. برای خروجی کوتاه بنویسید «فقط یافته‌های مستند و نتیجهٔ تست‌ها»؛ حذف جزئیات از گزارش به معنی حذف بررسی لازم نیست.

## enterprise-audit — ممیزی جامع

```text
با enterprise-audit کل repository را ممیزی کن. هدف و stack را از کد استنباط کن.
کد را تغییر نده. یافته‌ها را با شدت، طبقهٔ شواهد، path:line، سناریوی شکست و تست تأیید بده.
ریسک و فرضیه را از نقص اثبات‌شده جدا کن؛ محدودیت پوشش را صریح بنویس.
```

خروجی: هدف و دامنه، یافته‌های مرتب‌شده، برنامهٔ P0 تا P3 و شکاف‌های بررسی.

## audit-remediation — رفع گزارش موجود

```text
با audit-remediation یافته‌های گزارش docs/audit-report.md را با کد فعلی تطبیق بده.
همهٔ نقص‌های تأییدشده را با تغییر حداقلی اصلاح کن و regression test مرتبط را اجرا کن.
وضعیت هر یافته، محل تغییر و نتیجهٔ واقعی تست را گزارش کن. انتشار یا deployment انجام نده.
```

خروجی: وضعیت fixed/disproven/already-fixed/unresolved برای یافته‌ها همراه شواهد.

## security-audit — امنیت

```text
با security-audit مسیرهای API و احراز هویت src/ را بررسی کن.
ورودی کنترل‌شده، مجوز مالکیت، جداسازی tenant، secrets و logging را تا sink دنبال کن.
فقط گزارش بده؛ از دادهٔ dummy برای بازتولید محلی استفاده کن و مقادیر secrets را نمایش نده.
پیش‌شرط سوءاستفاده، path:line و تست پیشنهادی هر نقص را بنویس.
```

خروجی: یافته‌های امنیتی با دسترسی لازم، جریان ورودی، اثر و محدودیت شواهد.

## pr-review — تغییرات

```text
با pr-review branch فعلی را نسبت به merge-base با main بررسی کن.
فقط regressionهای ایجادشده یا بدترشده در این تغییرات را با trigger و path:line گزارش کن.
کد را ویرایش نکن و هیچ comment خارجی منتشر نکن؛ تست‌های مرتبط را در صورت امکان اجرا کن.
```

برای تغییرات commitنشده جای جملهٔ اول بنویسید «diff unstaged فعلی را بررسی کن». بدون Git، before/after واقعی ارائه کنید؛ agent نباید base بسازد.

## test-gap-analysis — شکاف تست

```text
با test-gap-analysis قراردادهای مهم src/payments/ را به assertions تست‌های موجود نگاشت کن.
سناریوهای مرزی، اجرای تکراری، شکست جزئی و cancellation مرتبط را اولویت‌بندی کن.
فعلاً تست اضافه نکن؛ برای هر شکاف محل کد، علت ناکافی‌بودن تست و setup/expected result بده.
درصد coverage را فقط اگر ابزار اندازه‌گیری اجرا شد گزارش کن.
```

خروجی: طرح تست اولویت‌بندی‌شده و نتایج اجراشده یا محدودیت اجرا.

## release-readiness — آماده‌سازی انتشار

```text
با release-readiness آمادگی نسخهٔ مشخص‌شده در VERSION را بررسی کن.
build، تست، بسته، نصب تازه/ارتقا/تکراری و rollback را در مقصد موقت بررسی کن.
go/no-go را فقط برای محیط‌های بررسی‌شده بده. tag، push، publish و deployment انجام نده.
```

خروجی: blockers مستند، هویت نسخه/بسته، نتایج تست و محیط‌های آزموده‌نشده.

## project-docs — مستندات و Wiki و نمودار

```text
با project-docs همهٔ مستندات مرتبط این پروژه را بررسی و موارد لازم را ایجاد یا به‌روز کن.
README، docs، Wiki محلی و نمودارهای معماری/sequence را با کد فعلی هماهنگ کن.
محتوای جدید فارسی باشد؛ زبان و ساختار فایل‌های موجود حفظ شود.
نمودارها قابل ویرایش باشند. لینک‌ها و ابزارهای build/render موجود را بررسی کن.
بدون Wiki checkout، پیش‌نویس محلی docs/wiki بساز و چیزی منتشر نکن.
```

خروجی: فایل‌های ایجاد/ویرایش‌شده، اصلاحات رفتاری مهم، checks و rendering/publishing gaps.

## audit-fix-loop — چرخهٔ اصلاح

```text
با audit-fix-loop گزارش docs/audit-report.md را بررسی و همهٔ نقص‌های تأییدشده را رفع کن.
پس از هر اصلاح تست و بازبینی تازه انجام بده و یافته‌های جدید مستند را به همان فهرست اضافه کن.
دامنهٔ بررسی نهایی کل repository باشد. تا رفع یافته‌های تأییدشده و یک دور کامل بدون
یافتهٔ actionable جدید ادامه بده. اگر مسدود شد، کار مستقل را ادامه بده و نتیجهٔ ناقص را صریح گزارش کن.
در پایان تعداد چرخه‌ها، وضعیت یافته‌ها، محل تغییر و نتایج checks را یکجا بده.
```

خروجی: گزارش پایان چرخه یا گزارش صریح کار ناتمام؛ هیچ تضمینی برای نبود همهٔ باگ‌های ممکن نمی‌دهد.
