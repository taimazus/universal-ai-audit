# استفادهٔ ترکیبی

ترکیب‌ها یک workflow ترتیبی در همان agent هستند؛ به سرویس، ارسال پیام بین agentها یا اجرای موازی خودکار نیاز ندارند. هر skill فقط هنگام مرحلهٔ خودش خوانده می‌شود. هماهنگ‌کننده یک فهرست یافته‌ها نگه می‌دارد؛ گزارش‌های کامل قبلی دوباره تولید نمی‌شوند.

## قرارداد انتقال

برای هر یافته: `ID | severity | evidence-class | path:line | trigger/impact | status | verification`.
خلاصهٔ دامنه، checks اجراشده/نتیجه و محدودیت‌ها نیز منتقل می‌شود. محل و نتیجهٔ تست پس از تغییر کد دوباره بررسی می‌شود؛ شواهد قدیمی به‌تنهایی اثبات رفع نیست. اصلاح، فایل‌های docs و نتایج readiness ممکن است بررسی‌های قبلی را نامعتبر کنند.

نقش‌ها: enterprise-audit/security-audit/pr-review کشف؛ test-gap-analysis طراحی تست؛ audit-remediation اصلاح؛ audit-fix-loop تنها مالک تکرار؛ project-docs مستندسازی رفتار نهایی؛ release-readiness اعتبارسنجی نهایی. تمام skillها الزامی نیستند. audit-remediation زیر audit-fix-loop مرحلهٔ اصلاح است، نه یک حلقهٔ دوم.

## ممیزی و اصلاح

```text
enterprise-audit → audit-remediation را روی کل repository اجرا کن.
اول گزارش مستند بساز، سپس نقص‌های تأییدشده را اصلاح و تست کن.
یک فهرست مشترک یافته‌ها و یک گزارش نهایی فارسی بده. انتشار انجام نده.
```

## امنیت و حلقهٔ اصلاح

```text
security-audit → audit-fix-loop را برای src/api اجرا کن.
آزمون امنیت فقط محلی با دادهٔ dummy باشد. یافته‌های تأییدشده را اصلاح کن، regression test
و بازبینی امنیتی را تکرار کن تا دور نهایی در همین دامنه یافتهٔ actionable جدید نداشته باشد.
پیش‌شرط‌ها، نتایج واقعی و موارد مسدود را در گزارش نهایی بده.
```

## PR و تست بدون تغییر کد

```text
pr-review → test-gap-analysis را برای branch فعلی نسبت به main اجرا کن.
کد را تغییر نده. regressionها و سناریوهای مهم پوشش‌داده‌نشده را با شواهد جدا گزارش کن.
فقط یک گزارش بده و نتایج checks مشترک را دوباره اجرا نکن مگر کد تغییر کرده باشد.
```

## اصلاح، مستندات و انتشار

```text
audit-fix-loop → project-docs → release-readiness را اجرا کن.
یافته‌های docs/audit-report.md را رفع و کل repository را بازبینی کن؛ سپس مستندات و Wiki محلی
و نمودارها را با رفتار نهایی هماهنگ کن. در پایان آمادگی نسخهٔ VERSION را دوباره بررسی کن.
اگر readiness نقص اثبات‌شده‌ای پیدا کرد، آن را به حلقه برگردان؛ docs/checks متاثر را تازه کن.
هیچ publish، push یا deployment انجام نده. یک گزارش نهایی فارسی بده.
```

## همهٔ skillها

```text
هر یازده skill را به صورت یک workflow هماهنگ روی پروژه اجرا کن:
project-builder نیازمندی‌ها و سناریوی پروژهٔ جدید را با پرسش‌وپاسخ روشن و دامنهٔ توافق‌شده را پیاده کند؛
task-orchestrator هماهنگ‌کنندهٔ مراحل و ledger مشترک باشد؛
enterprise-audit و security-audit برای کل کد؛ pr-review برای diff نسبت به main؛
test-gap-analysis برای سناریوهای مهم؛ audit-fix-loop با audit-remediation برای اصلاح و
بازبینی تا رفع یافته‌های تأییدشده؛ project-docs برای مستندات نهایی؛ release-readiness برای checks آخر.
پس از موفقیت checks، git-release-sync فقط تغییرات مرتبط را در commit محلی ثبت کند؛ push و tag و Release انجام نده.
اگر base موجود نیست، محدودیت PR را گزارش کن و بقیهٔ کار را ادامه بده.
یک ledger مشترک، یک مالک حلقه و یک گزارش نهایی بده. بررسی لازم را برای صرفه‌جویی توکن حذف نکن.
انتشار خارجی انجام نده؛ موارد واقعاً مسدود را ناتمام اعلام کن.
```

## ترکیب دلخواه و بودجه

برای پروژهٔ جدید، معمولاً `project-builder → project-docs → release-readiness` کافی است؛ review و حلقهٔ اصلاح فقط در مراحل مرتبط اضافه شوند. [راهنمای ساخت پروژه](project-builder.md) نمونهٔ کامل تعامل دارد. برای پروژهٔ موجودی که فقط ممیزی می‌خواهد، مرحلهٔ ساخت را حذف کنید.

```text
skillهای [نام‌ها] را به ترتیب [مراحل] برای [دامنه] استفاده کن.
اجازهٔ تغییر: [فقط گزارش / اصلاح کد / اصلاح تست / مستندات].
گزارش کوتاه با شواهد و نتیجهٔ checks بده؛ حداکثر [بودجه یا چرخهٔ انتخابی] را رعایت کن.
اگر شرط پایان تا محدودیت محقق نشد، گزارش ناتمام بده؛ نتیجهٔ موفق نساز.
```

این الگو هر زیرمجموعهٔ معنادار را پوشش می‌دهد؛ لازم نیست همهٔ جایگشت‌ها اجرا شوند. افزودن skill بی‌ارتباط مصرف را بالا می‌برد. خروجی کوتاه، خواندن انتخابی و استفادهٔ دوباره از شواهد ثابت مفیدند؛ حداقل مطلق توکن یا بهترین پاسخ برای هر مدل تضمین‌پذیر نیست.

## هماهنگ‌کننده و انتشار مجاز

```text
با task-orchestrator درخواست زیر را تا معیار پذیرش انجام بده: [درخواست].
skillهای مرتبط را انتخاب کن. پس از اصلاح و تست، project-docs را برای مستندات نهایی به کار ببر.
release-readiness آمادگی را بررسی کند؛ سپس git-release-sync تغییرات را در [remote/branch]
push و Release نسخهٔ [نسخهٔ جدید] را منتشر کند. این پیام مجوز همین push و Release است.
یک ledger و یک گزارش نهایی فارسی با نتایج واقعی، SHA و لینک Release بده.
```

task-orchestrator هماهنگ‌کنندهٔ مراحل است؛ در صورت نیاز به تکرار، audit-fix-loop مالک تنها حلقهٔ اصلاح می‌ماند. git-release-sync صرفاً مراحل Git و انتشارِ مجاز را انجام می‌دهد. اگر کار فقط گزارش یا ویرایش محلی است، این مرحلهٔ خارجی را انتخاب نکنید. هیچ skill تضمین «بهترین جواب برای همهٔ پرامپت‌ها» نمی‌دهد؛ معیار پذیرش و شواهد جای چنین تضمینی را می‌گیرند.
